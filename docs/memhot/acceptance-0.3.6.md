# 服务端 0.3.6：恢复有效补检

## 已复现的问题

0.3.5 的正式私人研究得到 12 条核对后的命题，却只有 1 组直接独立证据，未形成分析。工具轨迹显示首次网页检索和论文发现用完了 32 条发现容量，随后 4 次补检虽然查了实地部署、访谈和企业采用等不同方向，宿主都丢弃新命中并返回空 sources。给直接阅读保留的 8 个位置没有新网址可选，因此补检失效。

## 修复边界

私人 search、AIHOT 与 papers discover 共用发现准入逻辑。满 32 条时返回最多 8 条 leads，仅含标题、网址、短摘要及未读标记，无 sourceId。模型必须用 open_page 或 papers read 读取原文后取得来源 ID，才可提交可核对命题。总资料仍限制 40 条，满额仍可重读已有原文，不驱逐旧来源或改变已有引文身份。公共任务不开放任意网址或新的读取权限。

没有放宽独立证据、完整报告 ready 或引用审核要求；也没有用更长的无依据文字替代补检。未知付费请求继续受原围栏保护，回归必须使用新任务身份而非重放旧工具结果。

## 已验证

- Rust：233 passed、0 failed、3 ignored。新回归覆盖满发现容量仍暴露新网址、无可引用 ID、只返回 8 条、公共范围不泄露新读取能力、总容量耗尽后阻止新材料、已引用材料保持不变且可重读。
- 最终 Linux musl 服务器和 QA 示例已构建。新发布目录的 Linux Pi SDK 58 passed、0 failed、1 skipped，在 1 CPU / 384 MiB、禁网环境中验证，未调用模型。数据库副本迁移的用户与记录哈希保持不变。
- 0.3.5 真实语义修订/审核样本通过情况见上一验收；不能把它写成 0.3.6 新检索成功。本版本的实网任务单独记录。
